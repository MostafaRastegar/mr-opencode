# بررسی پروژه و پیشنهادهای بهبود دقت

پروژه شما یک قالب (template) برای راه‌اندازی جریان کاری **Orchestrator → Architect → Implementer → Reviewer** در OpenCode است. مستندات واقعاً جامع و دقیق نوشته شده — نقاط قوت زیادی دارد (مدل مجوزها، جداسازی نقش‌ها، اسکیل‌ها بر اساس نیاز، مستندات رفتاری). اما در «دقت کار» (به معنی صحت خروجی، کاهش خطا، و جلوگیری از تصمیم‌های اشتباه توسط agent) چند شکاف جدی وجود دارد. پیشنهادها را به دسته تقسیم می‌کنم:

---

## ۱. مشکل اصلی: Placeholderهای خالی و «not configured»

بزرگ‌ترین منبع کاهش دقت، این است که بخش قابل توجهی از ابزارها تا زمانی که دستی پر نشوند، **بی‌صدا** کار نمی‌کنند:

- `MIGRATION_CANDIDATES = []` → `db-status` همیشه «not configured» می‌دهد
- `TYPECHECK = null` → `check-file` هیچ کاری نمی‌کند
- `<TEST_CMD>`, `<TYPECHECK_CMD>`, `<LINT_CMD>` در AGENTS.md خالی

**پیشنهاد:** یک **اسکریپت `mro-doctor` یا `mro-init`** اضافه کنید که:

1. فایل‌های manifest پروژه را اسکن کند (`package.json`, `pyproject.toml`, `go.mod`, `Cargo.toml`, `pom.xml` و …)
2. حدس اولیه‌ای برای `<TEST_CMD>`, `<TYPECHECK_CMD>`, `<LINT_CMD>`, `<LOCKFILE>` بزند
3. به کاربر نشان دهد و **بعد از تأیید** جایگزین کند
4. اگر جایگزینی نکرد، حداقل یک هشدار صریح در شروع `/mro-orchestrate` بدهد (مثلاً یک preflight check که بگوید «۵ placeholder خالی است، ادامه می‌دهید؟»)

در حال حاضر تنها محافظ، قانون AGENTS.md است («وقتی `<...>` ماند، agent باید بپرسد نه حدس بزند») — که خوب است ولی اتکا به رفتار agent دارد. **جلوگیری سخت‌گیرانه‌تر بهتر از اتکا به حسن نیت مدل است.**

---

## ۲. ارزیابی پذیرش (Acceptance Criteria) شکننده است

`check-acceptance` فقط `- [ ]` / `- [x]` را می‌شمارد و خودش در مستندات اعتراف کرده:

- نمی‌تواند پوشش تست را تشخیص دهد
- نمی‌تواند تأخیر عمدی را از نادیده‌گرفتن تشخیص دهد

این یعنی agent می‌تواند با تیک زدن ساده، کار را «تمام‌شده» اعلام کند.

**پیشنهادها:**

- هر آیتم Acceptance را با یک **الگوی ماشین‌خوان** بنویسید، مثلاً:
  ```markdown
  - [ ] AC-1: GET /health returns 200 — verify: `curl -s -o /dev/null -w "%{http_code}" localhost:3000/health | grep 200`
  - [ ] AC-2: test_health_passes — verify: `<TEST_CMD> -k test_health`
  ```
  سپس `check-acceptance` بتواند دستور verify را اجرا کند (یا حداقل حضور آن را الزامی کند).
- در Reviewer، یک بخش اجباری «شواهد برای هر AC» بگذارید که بدون آن، review رد شود.
- حداقل، **تفکیک صریح** بین `- [x]` (تأییدشده با شواهد) و `- [~]` (تأخیر عمدی با دلیل) — تا `check-acceptance` بتواند این دو را از هم تشخیص دهد.

---

## ۳. حلقهٔ اصلاح فقط یک بار تکرار می‌شود

مستندات می‌گوید: «fix loop → re-run tests and reviews **once**؛ مشکلات باقی‌مانده به انسان». این محافظه‌کارانه است ولی در عمل:

- در پروژه‌های واقعی، یک بار review مجدد اغلب کافی نیست
- و از طرف دیگر، اگر مشکل ریشه‌ای باشد، یک دور دیگر هم حل نمی‌کند

**پیشنهاد:** به جای «یک بار»، از **معیار خروج شرطی** استفاده کنید:

- اگر تعداد CRITICAL کاهش یافت → یک دور دیگر مجاز است (حداکثر ۳ دور)
- اگر تعداد CRITICAL ثابت یا زیاد شد → توقف و ارجاع به انسان
- این را در state file ذخیره کنید تا در compaction گم نشود

همچنین **تفکیک CRITICAL از HIGH** در شرط توقف: HIGH می‌تواند به انسان ارجاع شود ولی CRITICAL باید صفر شود.

---

## ۴. Reviewer و Implementer مدل‌های متفاوت دارند، اما معماری یکسانی ندارند

مستندات می‌گوید Reviewer مدل متفاوت (`nemo`) دارد «برای جلوگیری از alignment bias». خوب است، اما:

- هر دو از یک **context protocol** (همان plan، همان diff) استفاده می‌کنند
- Reviewer **قبل از دیدن راه‌حل**، معیارهای پذیرش را نمی‌بیند؟ (مستندات نمی‌گوید)

**پیشنهاد:** Reviewer را «blind» کنید نسبت به rationale پیاده‌سازی:

- فقط diff + Acceptance Criteria + AGENTS.md را بگیرد
- **نه** plan را (یا حداقل نه بخش «چرا این‌طور پیاده شد»)
- این باعث می‌شود واقعاً مستقل قضاوت کند که آیا کد نیاز را برآورده می‌کند یا نه

همچنین یک **checklist اجباری** برای Reviewer بگذارید که هر آیتم باید صریحاً PASS/FAIL/N/A بگیرد — نه فقط «بررسی شد».

---

## ۵. محدودیت‌های امنیتی مستندشده ولی حل‌نشده

مستندات خودش اعتراف می‌کند:

- `read` جلوی `shell` را نمی‌گیرد → `.env` محافظت مطلق نیست
- `execute` و MCP tools فقط «جزئی» پوشش داده شده‌اند
- secret scan الگوی base64 یا split را نمی‌گیرد
- `--no-verify` hook را رد می‌کند

این‌ها برای دقت **خطرناک** هستند چون agent ممکن است به اشتباه فکر کند محافظت کامل است.

**پیشنهادها:**

- **به جای اعتماد به الگوهای regex**، از یک **allowlist** برای دستورات shell استفاده کنید: هر دستور باید صریحاً مجاز باشد (که الان هست، ولی `shell: "*" → ask` خیلی گسترده است).
- برای `.env`: **حذف فیزیکی** در sandbox (مثلاً اجرای agent در container با mount read-only) به جای اتکا به permission rules.
- یک مرحله **post-run audit** اضافه کنید: بعد از هر اجرا، `git diff` را برای الگوهای secret اسکن کنید و در صورت یافتن، session را flag کنید.

---

## ۶. Compaction و از دست رفتن state

مستندات می‌گوید compaction lossy است و «اگر API contracts گم شدند، `keep.tokens` را بالا ببرید». اما این واکنشی است، نه پیشگیرانه.

**پیشنهاد:** یک **state file ساختاریافته** (`state.json` یا مشابه) با schema صریح:

```json
{
  "feature": "...",
  "phase": "awaiting_plan_approval",
  "plan_hash": "...",
  "acceptance_criteria": [...],
  "changed_files": [...],
  "review_findings": [...],
  "test_exit_codes": [...],
  "approvals": {"plan": "2026-11-15T...", "final": null}
}
```

و Orchestrator **قبل از هر گام** این را بخواند/بنویسد. این از اتکا به context زنده کم می‌کند. مستندات می‌گوید «state file» وجود دارد، ولی مشخص نیست چقدر schema دارد — تقویت آن ارزشمند است.

---

## ۷. فقدان تست برای خود template

هیچ اشاره‌ای به تست کردن **خود قالب** نیست (نه agentها، نه pluginها). دقت ابزارهایی مثل `check-file`, `check-acceptance`, `mro-protect-secrets` تأییدشده نیست.

**پیشنهاد:** یک پوشه `product/tests/` با:

- تست واحد برای `check-acceptance` (شمارش و تفکیک `[x]`/`[~]`/`[ ]`)
- تست برای `mro-protect-secrets` با نمونه‌های مثبت/منفی (شامل base64 که می‌گویید پوشش نمی‌دهد — این را **مستند** کنید به عنوان known gap، یا پوشش بدهید)
- تست integration که یک پروژه dummy با placeholder پر شده را می‌سازد و `/mro-orchestrate` را اجرا می‌کند
- در `Verify` بخش، این‌ها را به عنوان gating اضافه کنید

---

## ۸. ارتقای مستندسازی رفتار (Behavior Docs)

`mro-behavior-docs` فایل `docs/behaviors/<feature>.md` می‌سازد. Reviewer باید آن را با diff مقایسه کند — خوب است. اما:

- چه کسی تأیید می‌کند که behavior doc **کامل** است؟
- اگر feature بعداً تغییر کند، doc قدیمی می‌ماند و **گمراه‌کننده** می‌شود

**پیشنهاد:**

- یک **CI-less check** (چون CI ندارید) در `/mro-deliver`: اگر `git diff` شامل فایل منبعی است که behavior doc مرتبط دارد، ولی doc تغییر نکرده → warn.
- یک فیلد `last_verified: <date>` در هر doc که فقط با اجرای مجدد تست‌ها به‌روز شود.
- در Reviewer، بخشی که صریحاً «آیا behavior doc با diff سازگار است؟» را PASS/FAIL کند.

---

## ۹. مدل‌های 9Router و «Insufficient balance»

مستندات می‌گوید مدل‌های پولی ممکن است با «Insufficient balance» شکست بخورند. این یک **حالت خطای غیرقابل پیش‌بینی** است که می‌تواند وسط workflow رخ دهد و state را خراب کند.

**پیشنهاد:**

- یک **preflight check** در `/mro-orchestrate`: قبل از شروع، یک درخواست کوچک به مدل بزنید و در صورت خطا، صریحاً متوقف شوید.
- یک **fallback model** تعریف کنید (مثلاً `9router/deep` → `9router/nemo` اگر اولی fail شد) با ثبت در state که fallback استفاده شد (تا کیفیت خروجی زیر سوال باشد).
- یا حداقل، error handling صریح در pluginها که error «balance» را تشخیص دهد و به انسان گزارش دهد، نه اینکه agent خودش سعی کند دور بزند.

---

## ۱۰. پیشنهادهای کوچک ولی مؤثر

- **`/mro-orchestrate` را idempotent کنید**: اگر وسط کار قطع شد، با همان slug ادامه دهد نه از صفر (state file).
- **زمان‌بندی و بودجه**: یک سقف توکن/زمان برای هر فاز تعریف کنید تا loops بی‌پایان شناسایی شوند (مکمل قاعده «دو turn بدون edit»).
- **لاگ ساختاریافته**: هر agent یک خط JSON با `{phase, files_changed, exit_codes, findings}` بنویسد — برای audit بعدی.
- **الگوی verify برای هر AC**: همان‌طور که در بند ۲ گفتم، این بزرگ‌ترین اهرم بهبود دقت است.
- **یک `mro-status` command** اضافه کنید که state فعلی، فاز، و کارهای باقی‌مانده را نشان دهد — برای انسان که می‌خواهد بداند کجاست.
